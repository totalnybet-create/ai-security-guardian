# P3 Network Guard — Android Capability Matrix

## STANDARD app

### DNS Guard over VpnService — IMPLEMENTED, ANDROID BUILD/DEVICE VERIFICATION PENDING

The current P3 Android path intentionally implements a **DNS-only local VPN**, not a fake full firewall.

The user authorizes Guardian through `VpnService.prepare()`. After consent, `GuardianDnsVpnService` establishes a TUN interface with:

- one private client address,
- one virtual DNS address,
- a route only for the virtual DNS `/32`,
- no default `0.0.0.0/0` or `::/0` route.

Therefore ordinary non-DNS traffic is not sent into an unfinished packet forwarder. The product may claim only `DNS Guard · DNS-only` after the TUN was actually established; it must not claim full TCP/UDP firewall protection.

For a DNS query routed to the virtual resolver:

1. Guardian parses IPv4/IPv6 + UDP metadata with bounded parsers.
2. Fragmented DNS is not classified/enforced from partial payloads.
3. DNS question metadata is parsed with bounded compression-pointer and question limits.
4. An explicit matching BLOCK rule returns a locally constructed `NXDOMAIN` response.
5. Allowed queries are forwarded through Android `DnsResolver.rawQuery()` on an underlying non-VPN network.
6. The upstream response must parse as a DNS response and have the same DNS transaction ID before it is injected back into TUN.
7. Upstream failure/overload returns explicit `SERVFAIL`, not a fake block verdict.
8. UDP/IP response checksums are generated by the local packet builder.

The service uses a bounded worker queue. If the queue is saturated, Guardian returns a bounded `SERVFAIL` path instead of allowing an unbounded in-memory queue to grow.

### Private DNS handling

Guardian does not intentionally downgrade Android Private DNS to a hand-written plaintext UDP resolver. The current Android upstream adapter uses the platform `DnsResolver` on an explicit non-VPN underlying network. This design must still be verified on real devices for Private DNS strict/opportunistic modes before production release.

### Flow ownership — PARTIAL / BEST EVIDENCE ONLY

On Android 10+ the active VPN may call `ConnectivityManager.getConnectionOwnerUid()` for TCP/UDP connection ownership. Guardian maps that UID to a package only when the mapping is unambiguous.

If Android returns no usable UID or multiple packages share the UID, `packageName` remains unknown. Guardian must not invent per-app attribution. DNS performed through Android system resolver infrastructure may naturally be attributable only to system resolver components rather than the originating application.

### Foreground lifecycle — REQUIRED

The Android VPN runs as a foreground service. The current manifest declares a VPN service protected by `android.permission.BIND_VPN_SERVICE` and a `specialUse` foreground-service type/permission. The actual Android SDK build and Play policy review remain mandatory release gates.

### Always-on VPN — NOT CLAIMED BY CURRENT PLAY/STANDARD IMPLEMENTATION

The current service explicitly does not advertise SUPPORTS_ALWAYS_ON. This avoids claiming restart/lockdown guarantees before failure recovery and full packet forwarding are verified.

A supported VPN app can later expose user-selected always-on behavior after Android build/device testing. Device/Profile Owner can use stronger managed-device policy separately.

### Lockdown VPN — NOT AUTO-ENABLED

Lockdown can break all normal networking if a VPN implementation fails. Guardian must therefore never silently enable or imply lockdown protection in the STANDARD edition.

### DNS privacy and logging

Ordinary successfully forwarded DNS queries are intentionally **not persisted** to the audit log. Security-relevant events such as explicit block, unresolved ASK, upstream failure, overload, malformed input and service failure may be audited with the minimum useful evidence.

This reduces the risk that Guardian's own local audit database becomes a browsing-history database.

### Payload visibility

DNS Guard does not decrypt TLS/QUIC payloads. Applications using their own DoH/DoQ, proprietary VPN/tunnel, literal IP destinations or other encrypted resolution path may bypass DNS-domain enforcement. The current UI states this limitation explicitly.

Full TCP/UDP forwarding/filtering remains a later P3 stage and must not be implied by the DNS-only implementation.

## DEVICE OWNER / PROFILE OWNER

A Device/Profile Owner can programmatically configure an always-on VPN package through `DevicePolicyManager.setAlwaysOnVpnPackage()`, including lockdown mode where supported. This belongs to the enterprise/managed-device adapter and is not a STANDARD capability.

Enterprise lockdown requires recovery and allowlist procedures because provider/VPN failure can remove ordinary application connectivity.

## ROOT / SYSTEM

Root/system variants may support different packet-filtering mechanisms, but they are explicitly out of the STANDARD core and must not be required for normal Guardian operation.
